# BGM・パリイ判定デバッグアプリ

既存の会話アプリと同じPython環境を使いますが、音声認識・LLM・音声合成は起動しません。
OGGの読み込みにはSoundFileを使用します。Windowsの対話可能なコンソールで実行します。
PowerShell、コマンドプロンプト、またはWindows Terminalを使用してください。
Git Bashのminttyや入力をリダイレクトした環境では、Windowsコンソールのキーイベントを取得できない場合があります。

## 起動

1. `data/bgm/`へ`easy.ogg`、`normal.ogg`、`hard.ogg`を配置します。
2. `config/bgm_settings.json`の区間を楽曲のリズムに合わせて編集します。
3. 既存の仮想環境を有効化し、プロジェクトフォルダで起動します。

既存環境を更新する場合は、アプリを実行する仮想環境で以下を実行してください。
新規セットアップ時はプロジェクトの依存関係として導入されます。

```bash
python -m pip install "soundfile>=0.13.1,<1"
```

起動コマンド:

```bash
python -m chambara_bgm
```

既存環境に新しいパッケージがまだ認識されない場合は、インストールせず次でも起動できます。

```bash
PYTHONPATH=src python -m chambara_bgm
```

PowerShellでの同等の指定は`$env:PYTHONPATH = "src"`です。
既存のセットアップ手順で`pip install -e .`を行った環境では、`chambara-bgm`でも起動できます。
設定と音声フォルダを変更する場合は次を使います。

```bash
python -m chambara_bgm --config config/bgm_settings.json --audio-dir data/bgm
```

起動後、Enterで設定と全曲を読み込み、簡単から開始します。Spaceはパリイ、Lはライフ減少、Qは終了です。
キーの押下・解放イベントを使用し、長押しは1回として扱います。

## ゲーム動作

Spaceは有効時間内なら成功イベントを通知します。成功しても曲は変わりません。
同じ周回の同じ区間で2回目以降の入力は失敗扱いになります。
Lはパリイの結果と独立して受け付け、簡単→普通→難しいへ進めます。
難しい段階のLは再生を停止し、アプリを正常終了します。曲の終端では同じ曲を繰り返します。
再度ゲームを行う場合はアプリを起動し直してください。開始時に設定を再読込します。

## 設定

`version`は整数の1、`stages`は`easy`・`normal`・`hard`の順に3件です。
各段階で`audio_file`と`parry_windows`を指定します。音声パスはBGMフォルダからの相対パスです。
音声はOgg Vorbis（`.ogg`）、または非圧縮16bit PCM WAV（`.wav`）を使用してください。
いずれもモノラルまたはステレオに対応します。Ogg Opusは未対応です。
WAVを引き続き使う場合は`audio_file`に既存の`.wav`ファイル名を指定してください。
OGGとWAVは段階ごとに混在できます。設定の構造と`version`は変更していません。
全曲を開始前にメモリへ展開し、デコード後のサンプル数から曲の長さを求めます。
形式の違いによってパリイ時刻設定の単位や判定方式は変わりません。

```json
"parry_windows": [
  {"start_ms": 1000, "end_ms": 1400},
  {"start_ms": 3000, "end_ms": 3400}
]
```

時間は現在の曲の現在の周回の開始からの整数ミリ秒です。開始は含み、終了は含みません。
区間は重複不可、隣接は可能です。読込時に開始順に並べます。
設定例の区間幅は簡単400ms、普通250ms、難しい100msです。
実際の曲に合わせて調整してください。曲の拍や区間幅を自動推定する機能はありません。
存在しないファイル、不正な形式、曲の長さを超える区間などは再生前にエラーになります。

## 将来の統合

`config.load_tracks()`が設定と楽曲を読込、`player.AudioPlayer`が音声を出力し、`engine.Game`が判定と遷移を行います。
コンソール処理は`cli`、Windowsキー処理は`keyboard`に分離しています。

```python
game = Game(tracks, player, emit=on_event)
game.start()
game.submit_parry()
game.submit_life_decrement()
game.stop()
```

呼び出しは同じ制御スレッドから時刻順に行ってください。
センサースレッドからは、取得時の`time.perf_counter()`と`game.generation`を付けてキューへ渡し、
制御スレッドが`submit_parry(timestamp, generation)`または
`submit_life_decrement(timestamp, generation)`へ渡す構成を想定しています。
世代番号が古い入力と切り替え完了より前の入力は破棄します。コンソールでは入力バッチを取得順に処理します。
ライフ信号で切り替えた後は、同じバッチの残りと切り替え中に蓄積した入力を捨てます。

通知する`Event`の`kind`は`parry_success`、`parry_failure`、`life_decrement`、`stage_changed`、`game_finished`です。
パリイ結果には`stage`、`loop`（1始まり）、`position_ms`、`window_id`（並べ替え後の0始まり）を含みます。
同一区間の成功は周回ごとに1回です。ライフ値、弱点点灯と弱点攻撃は外部側で管理してください。
`emit`は同期呼び出しなので、長い処理は通知先でキューへ渡してください。

## 検証と制約

```bash
python -m unittest discover -s tests -v
```

自動テストは音声デバイスを模擬します。実際の楽曲・出力機器では以下を確認してください。

- Spaceの境界付近での成功・失敗と、BGMが継続すること。
- パリイ未成功でもLで切り替わり、難しい段階のLで終了すること。
- 曲のループで再生位置と成功済み区間がリセットされること。
- Space・Lの長押しで重複成功や複数段階遷移が起きないこと。
- 出力機器の切断時に停止することと、終了後に音声機器を再利用できること。

判定は音声コールバックのDAC出力予定時刻とサンプル数を基準とし、画面は100msごとに更新します。
キー時刻はコンソールイベントをアプリが取得した時刻です。
Windowsのスケジューリング、コンソール入力の遅延、出力機器の遅延見積もりに影響されるため、
実機で同期精度を確認してください。表示の更新速度は判定精度と同じではありません。
DAC出力時刻と`stream.time`の共通の時計で位置を計算します。
ブロック終端から20ms以内の時刻更新遅れは短時間補間し、20msを超えた場合は
「再生時刻確認中」と表示してパリイ判定を保留します。Qとライフ減少入力は引き続き受け付けます。
コールバック更新が500ms以上停止した場合、出力異常、ストリーム停止はエラー終了します。
エラー表示には更新停止時間、ブロック長、音声デバイス名を含みます。
音声ブロックの長さは機器側で選択します（`blocksize=0`）。
